## 一条贯穿全部的主线（建议整场围绕它）

> **AI 的格式错误是最安全的错误。真正危险的是它"格式完全正确、语义悄悄偏了"。**
>
> 所以这套设计的重点不是"让 AI 少出错"，而是**"让 AI 的每一种出错都变成响亮的失败"**。

三个支撑论点：

1. **让 AI 只产出中间产物**，真正的改动交给已有的确定性工具 → 错误的爆炸半径被关在一个可读、可删的文件里。
2. **让未知即拒绝**（白名单 + fail closed + 分层退出码）→ 格式类、枚举类错误全部变成响亮失败。
3. **让效果可见、可撤**（逐文件 diff + 一键 reset）→ 剩下那些代码判断不了的语义偏差，交给人眼，而不是交给信任。

一个诚实的收尾（**这是最能加分的部分**）：

> 但我自己代码里还有五个静默失败的地方 —— 路径抽错会悄悄改别的目录、`inject_type` 写错会悄悄什么都不做、输出被截断没人检查、两份 schema 靠一句注释同步。**我知道它们在哪、为什么会这样、怎么修。**

### 收尾三句话

1. **AI 的格式错误是最安全的错误** —— 它会炸，而且炸在中间产物这一层。
2. **下游解析器的宽容度，决定了 AI 出错的后果。** 状态机的解析器严格，同一个错误在那里是响亮失败；注入器的解析器宽容，同一个错误在那里是静默无操作。**要让 AI 安全，先让解析器变严格。**
3. **要求用户"把话说清楚"是缓解，不是修复。** 修复是让说不清楚的时候，代码会喊出来。

## 预期追问与答法

**Q：你怎么保证 AI 不把我的代码改坏？**
A：我不保证 AI 不出错，我保证它没有权限改代码。它只产出一个中间文件（Markdown 规格 / JSON 配置 / 头文件），所有真实改动由已经写好并测试过的工具执行 —— libclang 解析 AST，Jinja2 渲染模板，g++ 编译验证。而且每次改动都以逐文件 unified diff 呈现，一键可回滚。

**Q：模型返回的格式不对怎么办？**
A：分两层。`json.loads` 挡语法，白名单挡语义 —— `tool` 必须是我认识的 5 个之一，否则落进 else 分支，什么都不跑、退出码 2。**关键是这是白名单不是黑名单**：拼错、大小写不对、返回 null、返回数组，全部落进同一个安全出口。
（诚实补充：目前 JSON 解析失败没有被优雅捕获，会打出 traceback、退出码 1。方向对 —— 绝不把垃圾往下游传 —— 但表现应该是"它拒绝了"而不是"它崩了"，这是我列的待修项之一。）

**Q：为什么用 enum 约束？**
A：因为**"合法值有限"等价于"非法值可以被机械识别"**。开放输出没法判断对错，闭集输出一比对就知道。而且 `unsupported` 本身是集合的一等公民 —— 如果只列 4 个工具，模型面对"今天天气怎样"会被迫在 4 个里挑一个，不是因为它笨，是因为我没给它"都不选"这个选项。

**Q：为什么要求生成的头文件保留原有风格？这不是审美问题吗？**
A：不是，是架构必需。下游 `interface_sync.py` 的整个工作前提是"新旧头文件之间的差异就是用户想要的变更"。模型如果重新排版，200 行差异里只有 2 行是真的 —— 一是我没法 review（而 review 是语义偏差的唯一防线），二是 diff 工具可能把"换了缩进的同一个方法"识别成"删一个 + 加一个"，于是去每个派生类里删 override、加空桩。**下游消费 diff 的时候，风格漂移就从"不好看"升级成"不可用"。**

**Q：这套东西最大的风险是什么？**
A：不是 AI 输出格式错 —— 那会炸，是安全的。是**静默失败**：路径抽错了会回退到默认目录，于是改了另一个地方的文件，前端还显示绿色成功；`inject_type` 写了个不认识的值会被 `if kind not in wanted: continue` 跳过，结果是 0 改动的"成功"；输出被截断没有检查 `finish_reason`，而截断的 Markdown 照样能解析。这三个都是"退出码 0 + 前端 success"。

**Q：能上生产吗？**
A：现在不能，它是一个一次性 demo 容器，代码里也是这么定位的。往生产走的第一批必做项：`/exec` 和 `/reset` 加鉴权（现在两个端点都是裸的，`/reset` 就是 `git restore .`）、路径参数限制在 tools 目录内（现在 `output` 可以指向容器内任意路径）、子进程加 timeout（现在会运行生成的二进制，死循环能把服务挂死）、并发隔离（现在共享一份 checkout）。

**Q：两份 schema 那个问题，为什么不一开始就做对？**
A：一开始的目标是"不碰已有工具就让它能被自然语言驱动"，所以 prompt 照着 `config.py` 的 schema 抄了一份 —— 抄的时候是对的，问题在于**没有任何机制保证它继续对**。修法很便宜：让 prompt 从 `TOOL_LABELS` / `TOP_LEVEL_KEYS` 这些已有常量生成，再加一个不需要 API key 的一致性测试。而且**我仓库里已经有这个模式的先例** —— `run_tests.py` 的 `check_example_configs()` 就是"每个示例 config 都必须通过校验"，防的是同一类漂移。

**Q：为什么不让 AI 直接生成代码/直接改文件？**
A：三个原因。一是可验证性：中间产物有 schema，可以校验；一段直接生成的 C++ 只能靠编译器和人眼。二是可复用性：所有真实改动走已有工具，意味着**AI 层删掉，工具照常工作**。三是爆炸半径：出错时坏掉的是一个可读可删的文件，不是散落在 13 个源文件里的改动。

**Q：如果要加第 5 个工具？**
A：现在要改 10 个地方，横跨 Python、JS 和 prompt 里的英文 —— 这是"枚举 + 白名单"用安全性换来的耦合。下一步应该做一张工具注册表，prompt 选项和前端按钮都从它生成，前端通过 `GET /tools` 拿。**但 4 个工具的时候不做是对的** —— 抽象的成本现在还高于它省下的维护成本。
