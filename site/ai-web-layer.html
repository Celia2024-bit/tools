The AI layer and the web console

Three tools, four scripts, a Markdown spec, a JSON config and a pair of header files — that is what you used to have to know. This layer replaces all of it with one sentence and one browser tab. A Gemini call picks the tool; a second Gemini call writes the one input file that tool already knows how to read; the tool itself runs unchanged. Nothing here makes the tools smarter, and nothing here lets a model edit your code. It is a front door, and it is built to fail closed.

Why a layer at all

Every one of these tools takes a strictly-formatted input, and authoring that input is the part nobody enjoys. The state machine wants a Markdown table with exact column headers and S000/T001 id conventions. The injector wants a config.json where exactly one of inject or remove is present. Interface Sync wants two header files that differ only by the change you meant to make. The tools are reliable; getting to the point where you can run them is the tax.

A language model is very good at exactly that step and only that step — turning a sentence into a structured file. So that is all it is allowed to do here. The division of labour is the whole design:

The one-line version

Intent comes from the model; correctness comes from the tools. The model writes an intermediate file. Deterministic code — libclang for the AST, Jinja2 for the templates, g++ for the proof — does everything that touches your sources. A bad generation is a bad intermediate file, which you can read, diff and throw away. It is never an unreviewed edit in your tree.

Architecture

Four hops, and each one is a process boundary you can test on its own. The browser never talks to Gemini, and the model never talks to the filesystem.

one request, end to end

     v
  flask    server.py                   snapshot the watched dirs, then
     |     subprocess: python nl_dev_tool.py "<prompt>"

  router   nl_dev_tool.py              call 1: which tool?  (JSON, 5 options)
     |
     +--> state_machine   --> nl_to_state_machine.py   call 2: Markdown spec
     |                       --> table_to_json.py --> json_to_mermaid.py
     |                       --> json_to_cpp.py  --> g++ --> run the binary
     |
     +--> aspect_injector --> nl_to_aspect_config.py   call 2: config.json
     |                       --> aspect_injector.py (libclang)
     |
     +--> interface_sync  --> nl_to_new_interface.py   call 2: new header
     |                       --> interface_sync.py
     |

     |
     +--> unsupported          --> exit 2. nothing ran.
     v

     |     JSON response
     v

The four rules the layer is built on

  1. The model only ever produces an intermediate artifact A Markdown spec, a JSON config, or a complete header file. Never a patch, never a shell command, never a direct edit. Each artifact is written to disk under its own name and reported, so it survives the run and you can keep it, edit it, or re-run the tool on it by hand.
  2. The format is pinned to a parser that already existed Each system prompt mirrors the schema of the tool that consumes it — the injector prompt mirrors config.py's top-level keys, the state machine prompt mirrors the tables table_to_json.py reads. The output is parsed by code, not read by a human, so ambiguity is a bug rather than a style question.
  3. Anything unrecognised stops the run A reply that is not JSON, or a tool name outside the five known values, becomes unsupported — not a best guess. Nothing is generated and nothing is touched.
  4. Every effect is shown and reversible The server diffs the tree around the run, so the answer to "what did it do" is a unified diff per file, not a log you have to trust. POST /reset puts the checkout back.

The intent router

nl_dev_tool.py is both the CLI and the thing the web API shells out to — there is no second code path for the browser. Its first job is one cheap Gemini call with minimal thinking and a 200-token ceiling, whose only output is a routing decision:

shell
export GEMINI_API_KEY=...
python nl_dev_tool.py "Add trace and validate logging to every function under
                      aspect_injector/test/src, but skip AlphaEngine.cpp"

# generate the intermediate artifact but run nothing
python nl_dev_tool.py "..." --no-run

# paths, when you would rather be explicit than let the router extract them
python nl_dev_tool.py "..." --old path/to/IObserver_old.h --src path/to/src -o out.json
ToolChosen when the request is aboutEffect
state_machinecreating or changing a state machinespec, diagram, C++, compiled and run
interface_syncchanging a C++ interface and its implementationsnew header, then every derived class
aspect_injectoradding or stripping trace / validate / guardrewrites the matched .cpp files
performance_monitorruntime behaviour over time — leaks, thread growthgenerates nothing. Answers with a link
unsupportedanything else at allnothing runs. Exit code 2

The JSON contract

The router prompt allows exactly one shape of reply, with no prose and no code fences. Two fields exist only to save you from typing paths twice: if the request mentions a header or a source directory, the model extracts them, and a CLI flag is the fallback rather than the other way round.

router output
{
  "tool":       "state_machine" | "interface_sync" | "aspect_injector"
                | "performance_monitor" | "unsupported",
  "old_header": "<path if the request mentions one, else null>",
  "src_dir":    "<derived-class root if mentioned, else null>",
  "reason":     "<one sentence; required when tool is unsupported>"
}

Failing closed

The reply is checked twice. First it has to parse as JSON — a stray fence is stripped, anything else raises immediately. Then the tool value has to be one of the five names the dispatcher knows; an unknown name falls into the same branch as unsupported, which prints why, lists what the assistant does automate, and exits without writing a byte. The refusal is spelled out in the prompt too: never force an unrelated request onto one of the tools. A helpful guess is the failure mode worth designing against, because a confident wrong tool rewrites source files.

Exit codeServer statusMeaning
0successthe tool ran to completion
2unsupportedout of scope — a normal answer, not a failure
3router_unavailablequota, bad key, service down. Nothing was generated
anything elseerrorthe tool itself failed. The log says where

Separating those four is what makes the console honest: "I will not do this" and "I broke" render differently, and neither of them is dressed up as a success.

Rate limits

A 429 from the router is retried up to three times with exponential backoff (5s, then 10s). If it still fails, the run ends with exit code 3 and a one-line message instead of a traceback — the key was bad, or the quota is gone, and either way nothing has been touched.

What the model writes, per tool

One generation call per run, with a system prompt written against the consumer's schema. Note what is not in this table: no tool receives generated code. They receive a specification, and they generate the code themselves, the same way they did before this layer existed.

ToolGeneratorArtifactThen handed to
state_machine nl_to_state_machine.py Markdown: config, context, state and transition tables, with S000 / T001 ids and exactly one initial state table_to_json.py → json_to_mermaid.py → json_to_cpp.py → g++ → run
aspect_injector nl_to_aspect_config.py config.json: exactly one of inject/remove, plus optional exclude and include_dirs aspect_injector.py (libclang AST)
interface_sync nl_to_new_interface.py the complete new header — same include guard, brace style, indentation, virtual destructor, and every method the request did not mention interface_sync.py (diff old vs new, walk derived classes)
performance_monitor — none. The tool is a live dashboard, so the answer is a URL your browser

Three details in those prompts are worth copying if you build something similar. Each one exists because of a failure it prevents:

Prompt ruleWhat it prevents
"Do not invent restrictions the user didn't ask for"a helpful extra exclude rule silently narrowing the run
"Preserve the file's existing style exactly"a correct interface that reformats the whole header and buries the real change
"Output ONLY the JSON / the Markdown / the header content"a code fence or a friendly sentence reaching a parser that was never written to skip one

The generated artifacts also get summarised into the log as the run goes — how many states and transitions the model designed, the +n / −n interface lines it changed, the inject rules it derived. That is what makes the log readable as a decision trail rather than a wall of subprocess output.

The HTTP API

server.py is a two-endpoint Flask app with CORS open, so the static site can live anywhere. It adds exactly one thing the CLI does not have: it watches the tree. A snapshot is taken before the run and after it, and the difference is the answer.

ConcernValue
Watched for diffsaspect_injector/test, sync_interface/test
Collected as artifactswhatever the log reported, plus state_machine/out and state_machine/output
Read back as textan allowlist of suffixes — sources, headers, .json, .mmd, .md, .html, .log; binaries are skipped
Per-file cap256 KiB, then truncated: true
Never walked__pycache__, .git, node_modules
Child processsame interpreter as the server, PYTHONUTF8=1, cwd pinned to the tools directory

POST /exec

prompt is the whole interface. Everything else is optional, and tool is not a tool selector — it picks one of four canned example prompts, which is what the preset buttons in the console send. A GET on the same path is a health check.

request
{
  "prompt":  "Update interface sync_interface/test/include/IObserver_old.h: remove
              OnConnected, add OnError(int err_code). Sync all derived classes
              under sync_interface/test/src",

  // optional
  "tool":    "sm" | "aspect" | "interface" | "monitor",  // use a preset prompt instead
  "old":     "<old header path>",   // --old
  "src":     "<derived class root>", // --src
  "output":  "<artifact path>",     // -o
  "no_run":  true                     // generate the artifact, run nothing
}
response
{
  "status":        "success" | "unsupported" | "router_unavailable" | "error",
  "tool_detected": "interface_sync",      // what the router actually picked
  "reason":        null,                  // filled in when it refused
  "dashboard":     null,                  // the whole answer, for the monitor
  "returncode":    0,
  "command":       "python nl_dev_tool.py ...",
  "logs":          "<stdout + stderr, verbatim>",

  "diffs": [ { "path", "name", "status": "added"|"modified"|"deleted",
              "additions", "deletions", "diff": "<unified diff>" } ],
  "diff_summary": { "files": 5, "additions": 20, "deletions": 10 },

  "artifacts": [ { "path", "name", "ext", "size", "lines",
                  "truncated", "content" } ],
  "mermaid": "<diagram source, state machine runs only>"
}

Biggest diffs come first, so the file the run actually cared about is at the top of the panel rather than alphabetically wherever. For a state machine run the server resolves the .mmd that this run produced by matching the spec it reported — the out/ directory still holds diagrams from earlier runs, and showing yesterday's diagram for today's request would be worse than showing none.

The marker protocol

The server learns what happened by reading the child's stdout. That makes these four line shapes an interface, not logging — they are ASCII-only, the path or URL is always last on the line, and changing them breaks the web page while the CLI keeps working, which is the kind of break that takes an afternoon to find. They are documented in both files for that reason.

LineRead as
-> AI selected tool: <tool>tool_detected, and which artifact dirs to collect
-> reason: <text>reason — why it refused
-> artifact [<label>]: <path>a generated file to read back into artifacts
-> dashboard: <url>dashboard — the monitor's entire answer

POST /reset

The injector and Interface Sync rewrite their own test sources in place. In a long-lived container the second run therefore no longer starts from the committed baseline, and a demo that quietly stacks edits on edits is a demo that stops making sense. This endpoint runs git restore . in the checkout and reports what it did: which tracked files were restored, which untracked paths (generated output, logs) were deliberately left alone, and — if any — which files are somehow still modified.

This one really does discard work

git restore . throws away every uncommitted edit to a tracked file in that checkout, not only the ones a tool made. It belongs to a throwaway demo container. The console asks for confirmation before calling it; that is the only thing standing in front of it, because the endpoint itself is unauthenticated.

The browser console

site/ai/index.html is one static file — Tailwind and Mermaid from a CDN, no build step, no framework, no state beyond the last response. It is embedded in the AI Assistant page and also opens on its own. What it renders is shaped entirely by which of the four statuses came back:

PanelShows
Prompt barthe textarea, four preset buttons kept in sync with the server's presets, and Reset workspace
Summary stripwhich tool the router picked, the status badge, changed files, +/− lines, generated file count, the exact command
Logstdout and stderr verbatim — the same text you would see in a terminal
DiagramMermaid, rendered. Absent from the layout entirely unless a diagram was produced, so the log takes the full width
Generated filescollapsed per file, filterable, with copy, HTML preview, and re-render for any .mmd
File changescollapsed per file, coloured unified diff, copy-the-whole-patch
Dashboard banneronly for the monitor: says plainly that nothing was generated, and links out

Two small decisions carry most of the page's weight. Both panels are collapsed by default — a run that rewrites 13 files would otherwise bury its own summary. And a refusal is rendered as its own amber badge, out of scope — nothing ran, with Changed files: 0 beside it, because the most important thing a tool that edits code can tell you is that it did not.

Running it yourself

The container exists because the dependency list is the real barrier: libclang, a matching clang Python binding, a C++ compiler, and the sibling util repo the injected code includes. None of that is worth installing to try a tool once.

shell
# container: g++, libclang, both repos, every Python dependency
docker build -t cpp-dev-tools:v2 .
docker run -p 8000:8000 -e GEMINI_API_KEY=... cpp-dev-tools:v2

# or locally, if you already have libclang and g++
pip install flask flask-cors google-genai jinja2 clang==14.0.6
export GEMINI_API_KEY=...
python server.py                # binds 0.0.0.0:8000

Then point the console at it — one constant at the top of the script in site/ai/index.html:

site/ai/index.html
const API_BASE = 'http://localhost:8000';   // or your deployed URL

The frontend is static, so it can be served by GitHub Pages, Vercel, or python -m http.server while the API runs somewhere else entirely — which is how the live version is deployed. The Dockerfile also patches one line of the clang binding so an unknown CursorKind from a newer standard library degrades to UNEXPOSED_DECL instead of raising; without it, parsing some headers simply stops.

Limits worth knowing

LimitWhat it means in practice
No authentication /exec runs code generation and /reset runs git restore, both unauthenticated. This is a demo service in a disposable container. Do not point it at a checkout you care about, and do not expose it without putting something in front of it
Diffs only cover the watched directories a request aimed outside aspect_injector/test or sync_interface/test still runs and still edits files — the page just will not show you the diff. Widen WATCH_DIRS before pointing it anywhere new
One run at a time the request is held open for the whole pipeline, compiler included. Two people clicking Run at once share one working tree, and on a free tier the first request after a sleep also pays the cold start
Two model calls per run routing and generation are separate calls against the same quota. The router retries a 429; the generator does not
The key comes from the environment server.py falls back to a placeholder string when GEMINI_API_KEY is unset, so a missing key surfaces as router_unavailable rather than a crash. Set it properly; never commit a real one in its place
Artifacts are text and capped 256 KiB per file, allowlisted suffixes only. A compiled binary is produced and run, but never shipped to the browser
A generated state machine is compiled, not verified g++ proves it builds and the binary runs. Whether the states and transitions are the ones you meant is still yours to read — which is exactly why the Markdown spec and the Mermaid diagram are put in front of you
